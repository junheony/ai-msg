# 게임 스튜디오 매니페스트

`games/<id>.json`은 게임별 저장소, 작업, 검증 기록과 산출물을 연결하는 목록입니다. 게임 파일을 복사해 보관하지 않습니다. 모든 경로는 읽기 전용 근거이며, `~/`는 대시보드 실행 계정의 홈 디렉터리입니다.

게임 스튜디오 수집기는 이 목록에서 게임 카드와 단계 진행, 작업 에이전트, 최근 산출물을 구성합니다. 스키마 계약은 `~/jobs/msg-studio/MANIFEST-SCHEMA.md`의 v1입니다. 필수 필드는 `id`, `title`, `stages`이며, 파일명과 `id`가 같아야 합니다. 알 수 없는 필드는 서버에서 무시하므로 설명을 임의의 `version`·`note` 필드에 넣지 말고 제목이나 해당 링크의 `label`에 적습니다.

## 상태와 근거 읽기

단계 순서는 `concept → assets → build → test → preview → approval → release`입니다. `stages[].evidence`의 실제 파일과 `approvals`를 바탕으로 서버가 상태를 계산합니다. 단계에 `state`를 직접 적지 않습니다. 연결된 작업의 `REPORT.md`가 `STATUS: BLOCKED: …`로 끝나면 상태를 다음 순서로 판단합니다. 같은 게임의 더 새로운 작업이 이어받았으면 `이어받음`(`name-N`→더 큰 N, `name`→`name-cx`, 또는 새 작업의 BRIEF/REPORT가 이전 단계로 명시), 보고서가 오너를 요구하면 `승인 필요`, 3시간 이내면 `막힘`, 그보다 오래되면 `중단됨`입니다. 단계를 막는 것은 최근 `막힘`뿐입니다. `jobs`는 `~/jobs/<작업명>/`과 연결되며 등록된 작업의 후속(`-2`, `-cx`)은 폴더가 생기면 자동으로 같은 게임에 묶입니다. `BRIEF.md`, `REPORT.md`, `pid.txt`, `run.log` 등의 기록으로 작업 상태를 보여줍니다.

**근거 파일이 있다는 것은 테스트 통과·품질 승인·출시 허가를 뜻하지 않습니다.** 실패한 감사나 중단된 실행도 중요한 근거입니다. `tests[].label`과 원본 보고서의 한계를 함께 읽어야 합니다. `approvals`의 `approved`는 해당 범위에 대한 명시적 오너 승인이 있을 때만 기록합니다. 기존 공개 배포 사실이나 로컬 패키지 선택 기록에서 승인을 추정하지 않습니다. `release`에는 실제 출시 기록을 넣고, 후보의 로컬 `release/index.html`이나 배포 방법 문서만으로 완료 처리하지 않습니다.

`repos`는 웹·Unity·백업 등 같은 게임에 속한 경로를 묶습니다. `readonly: true`는 원본이나 백업의 읽기 전용 표시입니다. `reference`는 파생 게임의 원본 게임 id로, 계보 링크에 사용합니다. `artifacts`는 실제로 일치하는 glob을 사용하며 최신 파일부터 제한된 수만 표시됩니다. 현재 목록은 `*`를 이용한 얕은 패턴을 사용합니다. 존재하지 않는 파일·예정 URL·가상의 승인 시각은 생략합니다.

## 현재 등록된 게임의 한계

| 게임 | 목록에 반영한 사실 |
|---|---|
| `neon-apex` | v3.0.0 공개 URL과 배포 검증 문서가 있음. 이번 작업은 공개 사이트를 새로 검사하지 않았으며, 별도 오너 승인 기록은 만들지 않음. 실물 휴대폰 성능 검증은 미수행. |
| `neon-apex-supercar` | v3.1.0 미공개 후보와 비공개 UI 저장소를 묶음. `백업`은 별도 게임으로 등록하지 않음. UI 후속 릴리스 검사는 원본 중단 후 분할 복구 실행으로, 단일 연속 실행 성공이 아님. |
| `bbai-brawl` | 웹·Unity codex 브랜치와 이전 fc74fb8 WebGL 빌드. AWS `/brawl/`는 **구버전 0.15.0-20261027-polish**이며 codex 변경은 미배포. 최신 성능 게이트 미달 및 Unity 985b3bc 재빌드 대기를 보존. |
| `bbai-updown-race` | 명시적으로 선택한 Unity 패키지는 승인된 패키지를 뜻하지 않음. 로컬 합성 soak는 약 240초와 10초로 운영 24시간 증거가 아님. `demo-video` 영상·캡처에는 플랫폼 소개 자료가 포함되어 레이스 검증으로 사용하지 않음. |
| `bbai-concepts` | 콘셉트 제안 문서만 존재. 게임·에셋·빌드·출시 근거 없음. |
| `game-kit` | 공용 TypeScript 엔진. 단위 테스트 153개 통과 보고. 실기기·실제 Workers/D1 미검증. 데모 테마 폰트가 OFL이라 CC0/자가제작 규칙 검토 전까지 에셋 단계 증거를 비워 둠. |
| `proto-merge`·`proto-stack`·`proto-gacha` | 빌드·스모크와 스크린샷 보고만 있음. 사람 플레이와 실기기 미검증, APK 미빌드. 번들 폰트가 OFL이라 에셋 단계 증거를 비워 둠. 원격 미연결. |

기존 게임의 에셋·라이선스 문서는 과거 출처 기록입니다. 목록에 포함됐다는 이유로 새 게임에서 재사용할 수 있다고 판단하지 않습니다. 신규 파이프라인은 CC0 또는 직접 만든 에셋만 허용하며, 복사한 참조의 권리 불명 에셋은 교체하고 `assets/LICENSES.md`에 기록합니다.

## 게임 추가

1. `templates/game/studio.json`을 `studio/games/<새-id>.json`으로 복사합니다. 모든 자리표시자를 실제 값으로 바꾸고 파일명과 `id`를 맞춥니다.
2. `repos`에 새 작업 디렉터리를 넣고, 파생 게임이면 `reference`에 원본 id를 적습니다. 새 게임은 `concept` 상태에서 시작합니다.
3. 존재하는 문서·산출물만 단계에 연결합니다. 아직 생성하지 않은 파일은 빈 `evidence` 배열로 남깁니다. 연결할 작업 디렉터리가 생긴 뒤 `jobs`에 추가합니다.
4. 아티팩트 glob은 실제 파일이 생긴 뒤 추가합니다. 다음 오너 결정이나 차단 한 개를 한국어 60자 이하의 `nextAction.text`로 적습니다.
5. 아래 검사를 실행하고 대시보드에서 카드·계보·근거 링크를 확인합니다. 머지·출시·배포·공개는 각각 오너의 명시적 승인 후 수행합니다.

```sh
node studio/validate.mjs
# 지정한 파일 또는 디렉터리만 검사
node studio/validate.mjs studio/games/neon-apex.json
```

Node.js 22.17 이상을 사용합니다. 검사기는 JSON 구조, 단계 순서, 한국어 다음 행동 길이, 일반 경로 존재와 glob 일치를 확인합니다. URL 접속, 테스트 실행, 승인 진위·출시 준비 판정은 수행하지 않습니다. 다른 호스트에서 검사하려면 먼저 동일한 근거 경로를 준비하거나 새 환경의 실제 경로로 수정해야 합니다.

참조에서 새 작업 디렉터리까지 생성하려면 [신규 게임 파이프라인](../docs/GAME_PIPELINE.md)과 템플릿 스크립트를 사용합니다. 기존 대상은 덮어쓰지 않습니다.

```sh
bash templates/game/scripts/new-game-from-reference.sh \
  --reference neon-apex --source "$HOME/games/neon-apex" \
  --id my-new-game --target "$HOME/bbai-codex/my-new-game" \
  --studio-root "$PWD" --title "새 게임" --dry-run
```

출력 계획을 검토한 뒤 `--dry-run`을 빼면 새 디렉터리와 매니페스트를 만듭니다. 원본 게임에는 쓰지 않으며, 새 git 저장소 초기화는 커밋·원격 설정·푸시·배포를 포함하지 않습니다.
